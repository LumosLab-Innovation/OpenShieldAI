# Defensive upstream evaluation

Reviewed: **2026-10-24**. Status: **design research; no integration has been implemented or validated**.

OpenShieldAI should be an independent defensive system: prevent avoidable exposure, investigate attacks, coordinate containment, and verify recovery. An OpenHunterAI report is a later evidence source, not the prerequisite for any of these capabilities.

## Evidence and decision rules

This review used official repositories, their license files, project documentation, and GitHub repository/commit metadata. [upstreams.json](upstreams.json) records the exact reviewed commit, source URLs, observed activity, and a proposed integration boundary. A recent commit is an activity signal, not proof of quality, security, support, or suitability. A research commit is not a recommended production release.

- **Integrate candidate:** a small, bounded dependency or external adapter worth validating first; no implementation commitment.
- **Evaluate:** potentially valuable, but permissions, workload, compatibility, or operational cost require a lab result.
- **Reference:** use a schema or architectural idea; do not import the whole project.
- **Reject as core:** does not fit the initial foundation; this is not a claim that the upstream product is ineffective.

No upstream code, rule pack, container, submodule, or binary is vendored. All entries remain `not_implemented`. Importing anything requires a separate review of its pinned release, transitive dependencies, license/notice obligations, security advisories, and the selected deployment boundary. Calling an API does not automatically settle all licensing questions.

## Architecture derived from the review

```text
Authorized telemetry / operator evidence / existing security tools
        ↓ authenticate source; bound parser/resource usage
Local intake → sanitized case store + provenance + source-health state
        ↓ restricted originals stay in the operator's separate evidence vault
Versioned events → deterministic detections → incident hypotheses
        ↓                         ↘ explicit coverage gaps
Bounded AI investigation: evidence-linked timeline, alternatives, next safe checks
        ↓ typed proposed actions; no credentials or arbitrary shell authority
Deterministic policy + scoped human approval
        ↓ action digest, target, parameters, TTL, authorization recheck
S3-only isolated least-privilege adapter → observed result → independent verification
        ↓
Containment / recovery status + residual risk + lessons learned
```

The first implementation (S1) uses local replay and proposals only; it has no target network access, live credentials or mutable adapter. S2 adds one read-only telemetry route and shadow decisions. The first containment-capable slice (S3) may add one supported reversible action adapter and isolated restore validation after its acceptance gates pass. In S1/S2, operators act through their existing approved processes and import receipts/postchecks; Shield performs no live action. The initial lab studies one Linux-hosted web application and web/host compromise; account compromise and ransomware/data loss remain additional study tracks. The proposed loop remains useful without OpenHunterAI. [PRD](../PRD.md), [architecture](../ARCHITECTURE.md) and [acceptance criteria](../ACCEPTANCE_CRITERIA.md) govern these stages; this research does not grant execution authority.

The initial deterministic policy stays inside the selected local application. OPA is an optional future policy engine, not a required service or approved replacement for that starting design.

This is compatible with [NIST SP 800-61 Rev. 3](https://www.nist.gov/publications/incident-response-recommendations-and-considerations-cybersecurity-risk-management-csf), which places response within wider risk management. [MITRE D3FEND](https://d3fend.mitre.org/about/) can supply technique vocabulary and relationships; a technique mapping alone is not proof that a deployed control works. For ransomware, the [CISA response guide](https://www.cisa.gov/stopransomware/ransomware-guide) supports prepared recovery, preserved evidence, containment, and restoration into a clean environment. These sources inform a design; this repository does not claim certification or official endorsement.

### Control boundaries worth retaining

1. **Evidence is untrusted data.** Attacker-controlled log lines, filenames, HTTP bodies, alerts, reports and retrieved documents cannot grant authority or alter rules. Source authentication establishes origin, not truth. Corroborate important claims; expose stale clocks, missing telemetry, contradictory observations and parser failures.
2. **Reasoning and execution are separate.** AI returns schema-validated hypotheses and action proposals. A non-LLM boundary owns authorization, allowed actions, permitted destinations, resource budgets and approval checks. Tool availability is a deployment capability, not an invitation for the model to invent commands.
3. **Approvals bind to the exact action.** Bind target identities, parameters, plan/policy digest, approver, expiry and single-use execution ID. Recheck at execution time; edits, scope expansion, drift or expiry invalidate approval. Unknown/timeout policy outcomes deny execution.
4. **Adapters carry minimal credentials.** Per-action/service credentials live outside prompts and reports. Avoid general root shells, fleet-wide administrator tokens and credentials permitting backup deletion. Scope outgoing network access and protect adapter endpoints from arbitrary URL requests.
5. **Action state is explicit.** `proposed`, `approved`, `running`, `failed`, `partial`, and `verified` have different meanings. An accepted API call is not containment. Mutation retries require idempotency or read-before-retry reconciliation. A successful reversal can restore configuration, but cannot undo exfiltration, evidence destruction or all credential revocations.
6. **Recovery preserves options.** Preserve evidence where feasible; restore to isolated clean destinations and verify application/data invariants before reconnecting. Never interpret a healthy process, matching file hash or completed copy alone as full business recovery. No backup/no usable source means `recovery_unavailable`, not AI reconstruction of lost data.
7. **Local use is deliberate.** Initial research and replay can run on local files with no outbound calls. A later local-model adapter needs the same evaluations as any provider. Cloud LLM, enrichment upload and community signal sharing require explicit egress policy; offline failure cannot trigger an undisclosed cloud fallback.
8. **Upstream content is reviewed supply chain.** Manual refresh only; record immutable ref, item path, license, author, source URL, content digest and accepted tests. No cron sync, automatic rule activation, floating `latest`, arbitrary plugin installation or full repository vendoring.

## Evidence required before a component is promoted

| Claim | Minimum useful experiment | Disqualifying result |
| --- | --- | --- |
| AI improves investigations | Same evidence, same tools and budget; compare deterministic playbook-only, analyst-assisted and AI-assisted runs; blinded scoring of correct next actions, evidence-supported statements, time and cost. | More convincing narrative without measurable correctness/time gain; unsupported claims presented as facts. |
| Detection works | Versioned benign and incident fixtures, held-out cases, source/field mapping checks, incident-level recall, precision and analyst workload. | Rule-hit count substituted for verified incidents; silent schema mismatch. |
| Enforcement is safe | Observe-only replay, legitimate-traffic regression, bounded canary, TTL and allowlist tests, measured enforcement plus verified reversal. | Broader target affected, health/SLO breach, approval bypass, or decision recorded without observed effect. |
| AI withstands hostile evidence | Poisoned logs/reports, conflicting sources, malicious tool text and secret canaries; record model, prompts, seeds/run count and every tool attempt. | Any unapproved mutation, secret egress, authority escalation or suppression of safety-critical evidence. A zero-failure sample is a release condition, not a universal safety guarantee. |
| Recovery is possible | Approved restore rehearsal into a clean destination; snapshot/integrity checks plus application-specific assertions; measured recovery point/time and operator signoff. | Restoring into production by default, inability to open/use recovered data, hidden loss, or backup deletion credentials in the AI plane. |
| Offline operation works | Disable external network, use local fixtures/policy/model if configured, test provider failure and adapter capability degradation. | Unexpected outbound traffic, silent cloud fallback, or fabricated success. |
| Operations remain bounded | Log floods, malformed/oversized inputs, slow/unavailable tools, duplicate events, queue overflow and stale telemetry. | Unlimited resource growth, unreported evidence loss, or repeated mutations after uncertain completion. |

Initial safety gates should require zero observed unauthorized mutations, cross-scope actions, secret-canary leaks and fabricated verification in the documented evaluation suite. Performance/quality thresholds need an explicit baseline and supported workload; they must not be invented from upstream marketing claims.

## Sequencing and rejected shortcuts

1. **Research contract first:** define supported incident scenarios, threat model, evidence/action schemas, harm budget, independent verifier and evaluation dataset contract.
2. **Local replay prototype:** collect no production credentials; compare deterministic playbooks with AI assistance on labeled incident evidence. Validate source hygiene and coverage-gap reporting.
3. **S2 read-only pilot:** choose an existing customer telemetry source and add one read-only ingestion adapter after S1 acceptance. Shadow response proposals remain advisory; no enforcement or restore executor is available.
4. **S3 approved response and recovery:** only after S3 acceptance, add one narrow reversible containment route and approved isolated restore validation. Choose Coraza/CRS *or* CrowdSec based on the actual environment and experiment. Backup inventory is read-only before this stage. Broaden endpoint/cloud adapters only after their own permission and failure-mode tests.
5. **Later collaboration:** ingest a signed/versioned sanitized OpenHunterAI report as vulnerability/exposure context; keep operational incident status and attack findings distinct. Retest and production response each retain separate scope/approval decisions.

Defer full SIEM replacement, a new EDR agent, a general SOAR app marketplace, a new WAF engine, autonomous fleet-wide remediation, arbitrary generated shell execution, custom malware decryptors and claims of preventing every AI attack. None is needed to demonstrate better investigation, safer containment or verified recovery.

Research limits: this review did not deploy these tools, benchmark them, verify every dependency, or obtain a legal compatibility opinion. All proposed adapters and benefits remain hypotheses until the experiments above pass.
